Multiplayer AI

A native desktop app for chatting with AI models and sharing conversations across devices. Connect local or hosted models, create workspaces, and invite people to work in the same chat without sharing your provider credentials.

The project is under development. The desktop app, authenticated device relay, and model adapters are available. The separate Connection Server in src/ is a development component with no client authentication or session management.

Get started

You need Python 3.13 or newer. Download or clone this repository, then open a terminal in its root folder, where requirements-desktop.txt lives.

Windows (PowerShell):

python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-desktop.txt
.\.venv\Scripts\python.exe -m desktop_app

macOS / Linux:

python3 -m venv .venv
./.venv/bin/python -m pip install -r requirements-desktop.txt
./.venv/bin/python -m desktop_app

On Linux, unlock a Secret Service keyring before launching. The app saves secrets in your operating system's credential store: Windows Credential Manager, macOS Keychain, or Linux Secret Service.

To open the app again, run the last command. Setup creates the local relay and device identity automatically; you do not need to start a server separately. For Conda or development setup, see the development guide.

Send your first message

  1. Open Providers and choose your provider.
  2. Enter its API key and select a model. For local models, install Ollama first, then use Cookbook to download and run a model.
  3. Click Connect agent. Chat opens automatically; send a message.
  4. Use Invite a device to bring someone into the workspace chat with its existing history. They open directly into that chat after joining. Invite to conversation shares a separate model conversation.

The first imported model becomes the default. You can add more models and assign specialist roles later. See the desktop guide for those steps.

Architecture overview

Each owned workspace starts an authenticated relay on its host device. Desktop clients and model agents connect to that relay; a model agent calls the local Ollama runtime or its configured hosted provider. Each workspace controls its own relay and data, without a mandatory project-operated central service. Within a workspace, communication still passes through one host rather than a peer mesh.

flowchart LR
    UI[Host desktop UI] --> Runtime[Workspace runtime]
    Runtime --> Relay[Authenticated workspace relay]
    Guest[Invited desktop or device client] <-->|WebSocket / HTTP| Relay
    Relay <--> Agent[Model agent on its device]
    Agent --> Ollama[Local Ollama runtime]
    Agent --> Cloud[Hosted or compatible model API]
    Runtime --> Data[(Local settings and SQLite history)]
    Relay --> History[(Shared conversation history)]
    Agent --> Vault[Device OS credential store]
  • Desktop and runtime: PySide6 draws the interface. A dedicated Qt thread runs the asyncio networking runtime so provider calls and relay work do not block the UI. Owned workspaces retain their relays when you switch pages or workspaces.
  • Communication and membership: network_a2a/ authenticates device tokens, enforces group and conversation access, discovers connected agents, and routes requests and replies over WebSockets or authenticated HTTP. Invitations give each device its own identity.
  • Models and orchestration: provider adapters run on the model's device. The workspace's Head answers directly or delegates up to three ordered tasks to authorized specialists, then combines their results. Provider keys and private model instructions stay on the device that runs the adapter.
  • Persistence: JSON files store preferences and workspace configuration; SQLite stores chat archives and shared history. Secrets use the OS credential store. Guests cache history locally for offline reading, while the host coordinates new shared messages.
  • Cookbook and attachments: Cookbook combines a bundled or refreshed model catalogue with local hardware readings and controls local Ollama models. Images and PDFs are prepared on the sending device before being included in model requests and shared chats.

The separate Connection Server in src/ can forward agent requests to the relay through its gateway. It uses a different protocol and is not part of the normal desktop startup. See the development architecture guide for the module map.

Limitations

  • LAN-first sharing and WAN infrastructure: the default sharing workflow targets a trusted LAN. Communication across networks needs a reachable server or relay, plus TLS and network configuration. To avoid depending on a WAN communication service whose server component was not available as open source, we opted out of bundling that service and kept the default experience locally hosted and open source. Ownership is decentralized across workspaces, but each workspace still depends on its host relay. The relay code in this repository is open source and can optionally be self-hosted for WAN access using the network setup guide. The app does not provide managed WAN hosting, NAT traversal, or automatic router and firewall configuration.
  • Host availability and scale: shared messaging requires the host to be online. Connections and in-flight requests live in one relay process; run one worker and one replica. There is no automatic host failover, durable offline request queue, or multi-replica routing. Reconnection is supported, but failed or interrupted requests are not automatically replayed.
  • Transport privacy and administration: plain ws:// LAN traffic is unencrypted. WSS encrypts the device-to-relay connection, but the relay can read payloads; end-to-end encryption is not implemented. Device tokens, group isolation, owner controls, and member removal exist, but there is no comprehensive administration console or fine-grained organization policy system. Chat archives are stored locally without application-level encryption.
  • Workspace membership: the desktop currently supports one joined remote workspace at a time. Each connected device or agent needs a distinct identity; the relay rejects simultaneous connections using the same identity.
  • Model context and response handling: the saved archive is complete, but requests use at most 100 recent messages within byte limits, so older context may be omitted. Adapters return complete responses rather than streaming tokens to the UI. Delegation has a four-minute overall limit and can increase provider calls, latency, and cost; assigned roles do not verify model abilities.
  • Attachment limits: up to eight files per message, 20 MiB per source file, and an 8 MiB prepared-request budget. PDFs are limited to 200 pages; page images are included only for PDFs of 16 pages or fewer. Image and scanned-PDF support depends on the selected model's vision capabilities.
  • Cookbook coverage: compatibility verdicts estimate memory and storage fit; they do not certify performance or successful execution on a device. Hardware detection and model metadata can be incomplete. Built-in download and run controls target local Ollama GGUF builds, and recommendations describe the current device rather than every device in a workspace.
  • Agent interoperability and guardrails: the relay is a custom transport, not a standard A2A endpoint with Agent Cards or streaming. The local A2A bridge supports synchronous JSON responses. MCP integration is not implemented. Routing validates access, task assignments, and payload sizes, but the app has no dedicated content-moderation or prompt-injection defense layer. Models answer through APIs; returned code is not automatically executed.

Future improvements

These are planned directions, not features available in the current release.

  • A more developed Cookbook: expand model coverage, setup recipes, and measured compatibility reports across operating systems and hardware. Let users inspect models that could run on other workspace devices, with device owners controlling which hardware details they share.
  • MCP support: add Model Context Protocol clients for tools, resources, and prompts, with explicit permissions and controlled access to external systems.
  • HDFS-inspired architecture: implement a distributed storage layer for shared history and attachments, using replication and recovery alongside durable messaging and host failover to make device communication more robust.
  • Administration controls: extend existing owner and membership controls with granular roles, model and tool permissions, audit history, usage limits, and centralized workspace policy management.
  • Improved AI guardrails: strengthen prompt-injection defenses, sensitive data handling, input/output policy checks, and approval controls for future tool actions, backed by safety evaluations.

Connect a model

  1. Open Providers or click Connect a model.
  2. Choose a provider and enter its API key. Local Ollama usually needs no key. For Bionic GPT or a custom compatible server, enter your deployment's API root.
  3. Select a model from the Model dropdown, or enter its exact ID. Find models refreshes the list.
  4. Click Connect agent. The app opens Chat and runs the adapter automatically.

For Ollama, install Ollama and download the model first. You can do the download from Cookbook. The app starts a stopped local Ollama server when needed; remote servers must already be running.

The first imported model becomes the default. Additional imports keep the same chat history and get distinct agent names. Start automatically restores a model connection when you reopen the app.

Use Providers → Edit model to change the model, instructions, image support, or internet access. Model names stay fixed to preserve existing chats. Edit a remote model on the device that runs it. See provider adapters for supported providers and endpoint settings.

Chat and model orchestration

Send a message in Conversations to use the default model. Basic chat needs no purpose, role, or delegation settings. If the saved default is offline, another available imported model answers. Follow-up messages include recent conversation history.

Use the conversation picker to switch saved chats. Start a message with @model-name to choose which model answers in the current conversation. It receives the recent history and attachments, and its reply stays in the same thread. This also works in shared chats without changing their default model. A bare model mention waits for you to add a message. Mentioning a user opens their direct conversation; inline mentions stay as message text. You can still open a separate model chat explicitly from Agents.

Type / for command suggestions or @ for agents and users. Accept a suggestion with the arrow keys and Enter or Tab, then send the completed command. Use Shift+Enter for a new line and // to send a literal leading slash. Command results stay out of model prompts and shared conversation history.

Optional specialist delegation

Assign a role with /set, or edit a model's purpose and permitted tasks and enable Allow automatic delegation to this model. These are your routing preferences, not a test of the model's abilities.

The Head can select a specialist or plan up to three ordered tasks, then combine their results. It checks workspace access, online status, task permissions, and image support before dispatch. Ordinary greetings use one model directly. If planning fails or no specialist is available, an available default model answers the original request. Failed worker requests are not automatically replayed.

Automatic routing uses models imported by the workspace owner or explicitly chosen by the owner as coordinator. An invited model's published role alone does not grant access to workspace chat context. Other invited models remain available through direct chats. Replies show which model produced them.

Assigned models receive the relevant history and attachments. Purpose descriptions are shared with the workspace; provider keys, API roots, and private model instructions stay on the model's device. A request can make several provider calls and has a four-minute overall limit. Models answer through APIs; this does not give them filesystem access or execute returned code.

Cookbook: find, download, and run local models

Open Cookbook from the top bar. It estimates which model builds fit your device's RAM, GPU memory, and free storage. Search or filter the catalogue, then choose a context length and quantization. Fit verdicts are estimates rather than benchmarks. All models shows the full catalogue if nothing is recommended.

  1. Install Ollama on this device.
  2. Click Refresh local models to list installed and running models.
  3. Choose a build and click Download. Progress appears under Local models. Cancel download stops the request; Retry reuses Ollama's partial files.
  4. Click Run to load the model with the selected context. Stop unloads it without deleting its downloaded files.
  5. Click Use in chat, then Connect agent to add it to this workspace.

Downloads continue while you switch pages or workspaces. Closing the app cancels pending requests; downloaded files stay in Ollama's model store. Files are shared across this device, while agent connections belong to their workspace.

The page opens from a bundled or saved catalogue. Refresh from Hugging Face updates metadata; Download fetches model files through Ollama. Mirror settings apply to metadata refreshes. Native download and Run controls support local Ollama GGUF builds; connect other engines through Providers.

Create and manage workspaces

Click + → Create a workspace, enter a name, and switch workspaces using their initials in the rail. Each has its own chats, models, members, and invitations. Owned workspaces keep their relays and models running while you view another workspace. Closing the app stops them.

Workspace settings shows members and online status. Owners can rename the workspace, invite members, or Remove a member to revoke access and disconnect it. Removing a local model also removes its configuration and saved credentials.

Delete workspace removes that owned workspace's local chats, configuration, and credentials and disconnects its members. Deleting the last owned workspace creates a fresh one. Leave workspace removes a joined workspace's local history and saved invitation. If the host is reachable and manages membership, leaving also revokes the invitation there; otherwise ask its owner to revoke it.

Invite another device

On the host:

  1. Open your owned workspace and click Invite a device.
  2. Create a new identity for the other device.
  3. For a trusted LAN, enable Share this relay on my local network and select the Wi-Fi or hotspot adapter under Host network.
  4. Use an address the other device can reach and share the invitation privately. Each invitation contains a separate private token.
  5. Keep the host app open and allow the displayed port through its firewall.

On the invited device:

  1. Click + → Join a workspace.
  2. Paste the invitation, or enter the relay address and device token.
  3. Join and wait for the connection. The app opens the workspace chat with its existing messages, attachments, and replies. The workspace is remembered for next time.

Normal workspace invitations share the same persistent chat. The host's Chat entry opens that thread too, so everyone sees subsequent messages and AI replies. Additional devices join the same history instead of creating separate chats.

Use a different invitation for each device. An identity already connected on one device cannot be reused on another. One joined workspace is supported at a time; switch to it and use Leave workspace before joining another.

LAN sharing stays enabled after you opt in. Create a fresh invitation if the host's network address changes. Plain ws:// LAN connections are unencrypted; use a reachable wss:// relay for internet or untrusted networks. See network setup for hosting with TLS. The app does not configure cloud hosting, router forwarding, or firewall rules.

Share an AI conversation

Invite a device shares the workspace's main chat and its existing history automatically. To invite someone to a separate model conversation:

  1. Open the model's chat and click Invite to conversation.
  2. Create a new invitation for the other device.
  3. On that device, paste it into + → Join a workspace.

Both devices see the existing messages and subsequent replies. Either participant can send the next message, and the model receives their combined history. Shared chats are visible to their invited devices, including their attachments.

Shared history and membership persist on the host; guests keep a local copy for offline reading. Invitations survive host restarts unless revoked. The host must be running to send new requests and synchronize messages.

Model internet access

Internet access is off by default. To enable it, edit a model and select Allow this model to search the web, then:

  1. Choose Ollama web search and enter a key from your Ollama account. This works with any model provider and requires a separate search key, even for a local model.
  2. Choose Automatic to let the model request searches, or Always to search before each answer. Automatic mode depends on the model's judgment.
  3. Click Test web search, then save.

Alternatively, choose SearXNG and enter your search server address, separate from the model's API root. Its settings.yml must enable JSON search:

search:
  formats:
    - html
    - json

The app supplies up to five result snippets and source links, not full pages. Queries go to the selected search service. Search keys and model keys are stored separately in the OS credential store; leave a key blank when editing to keep it.

Attach images and PDFs

Click Attach images / PDFs in a chat, select your files, and send a question or the files alone. Remove discards a prepared attachment before sending. Files are prepared locally; sending shares their content with the selected provider and, in shared chats, invited members. Saved history retains attachments for follow-ups.

Text PDFs work with any model. Images and scanned PDFs need a vision-capable model with image support enabled. The checkbox does not add vision to a text-only model.

Saved data and recovery

The app restores your identity, selected workspace, chats, drafts, and models marked Start automatically. Settings and chat archives live in:

Platform

Preferences directory

Windows

%LOCALAPPDATA%\MultiplayerAI

Linux / macOS

$XDG_CONFIG_HOME/multiplayer-ai, defaulting to ~/.config/multiplayer-ai

Use python -m desktop_app --data-dir PATH to choose another directory. It contains settings.json, workspaces.json, and history.sqlite3; additional workspaces store separate data under workspaces/<workspace-id>/. Tokens and provider keys stay in the OS credential store.

The complete chat archive is saved. Model context includes up to 100 recent messages within about 190 KiB of text and the 8 MiB prepared-request limit. Older messages remain readable. Interrupted requests are never automatically replayed.

If an identity's token is missing, the app replaces that identity and preserves other preferences. Rejoin affected remote workspaces with fresh invitations. Settings → Reset local identity deliberately replaces all local identities and also requires fresh invitations for joined workspaces.

Settings includes theme and animation preferences. Resources shows local CPU, memory, and disk usage.

Ollama on a laptop

You can configure providers directly in the native desktop app. Choose Providers, select a model, and click Connect agent. The app starts the adapter automatically; no terminal command is needed. See DESKTOP_GUIDE.md.

Start Ollama and pull the model you want (for example ollama pull llama3.2). Set this device's relay token, then start its agent:

$env:A2A_TOKEN = 'this-devices-relay-token'
python -m network_a2a --server wss://agents.example.com/connect --provider ollama --model llama3.2

The laptop keeps the process running to handle requests. For an Ollama instance on a trusted LAN, set OLLAMA_BASE_URL to its HTTP root and explicitly add --allow-insecure-provider. For Ollama Cloud, set the documented HTTPS API root in OLLAMA_BASE_URL and its key in OLLAMA_API_KEY.

Bionic GPT

Obtain an API key and a model ID from your Bionic GPT deployment:

$env:A2A_TOKEN = 'this-devices-relay-token'
$env:BIONIC_API_KEY = 'your-bionic-api-key'
$env:BIONIC_BASE_URL = 'https://your-bionic.example.com/v1'
$env:A2A_MODEL = 'your-bionic-model-id'
python -m network_a2a --server wss://agents.example.com/connect --provider bionic

Use http://localhost/v1 for a local deployment. API roots are operator configuration; peers cannot supply URLs or API keys in requests.

Cloud providers

For OpenAI, set OPENAI_API_KEY and choose a Responses-capable model available to your account:

$env:A2A_TOKEN = 'this-devices-relay-token'
$env:OPENAI_API_KEY = 'your-openai-api-key'
$env:A2A_MODEL = 'your-openai-model-id'
python -m network_a2a --server wss://agents.example.com/connect --provider openai

For Claude or Gemini, use --provider anthropic or --provider gemini, set the corresponding key from the table, and select that provider's model ID. The same pattern works for Groq, DeepSeek, Mistral, and OpenRouter.

Custom compatible servers

For a local chat completions server (for example one you run with LM Studio or vLLM), configure the API root including its version path:

$env:A2A_PROVIDER_BASE_URL = 'http://localhost:1234/v1'
$env:A2A_MODEL = 'your-loaded-model-id'
python -m network_a2a --server wss://agents.example.com/connect --provider openai-compatible

Set A2A_PROVIDER_API_KEY if that server needs authentication. Compatible means it accepts model, messages, stream: false, and max_tokens, and returns choices[0].message.content. Provider-specific model features can require an additional adapter.

Send requests from another device

Use a different relay identity's token on the sending device:

$env:A2A_TOKEN = 'sending-devices-relay-token'
python -m network_a2a --server wss://agents.example.com/connect --to laptop_bob --payload '{"text":"Explain how agents communicate over a network."}'

The result has a consistent shape:

{
  "text": "The model's response",
  "provider": "ollama",
  "model": "llama3.2",
  "usage": {"input_tokens": 25, "output_tokens": 60},
  "finish_reason": "stop"
}

Usage fields and finish reasons follow the provider's naming; Ollama token counts are mapped to input_tokens and output_tokens. A truncated response can still contain text; inspect finish_reason before treating it as complete.

Accepted inputs are a JSON string, {"text":"..."}, or explicit conversation history:

{
  "messages": [
    {"role": "user", "content": "My project uses Python."},
    {"role": "assistant", "content": "What would you like to build?"},
    {"role": "user", "content": "Suggest a layout for an agent adapter."}
  ]
}

History must start and end with a user message. Assistant content is text; user content can also be a list of text, document, and image parts. The desktop app prepares PDF text and base64 images and maps them to each provider's native API. Set vision=True in ProviderConfig for a vision-capable model. There is no shared memory in the adapter: include history in each request, which prevents different peers' conversations from being mixed.

Desktop model settings expose image support, Ollama web search, and SearXNG. Python ProviderConfig accepts web_search="auto" or "always"; the default is "off". Set search_provider="ollama" with search_api_key, or use the default search_provider="searxng" with searxng_url. Automatic mode permits the model to request a search, then generates an answer from bounded result snippets with source URLs. This is a model decision, not a comparison with its training dataset. See the setup and attachment limits in DESKTOP_GUIDE.md.

Local settings and failures

Optional settings: --system-prompt (or A2A_SYSTEM_PROMPT), --max-tokens (default 1024), --provider-concurrency (default 4), --provider-timeout (default 55 seconds), --provider-base-url, and --api-key-env. Provider URLs, models, keys, system instructions, and token budgets are controlled locally. Remote requests cannot override these settings.

The provider timeout includes queueing. Keep it below the relay timeout (default 60 seconds) and the AgentClient timeout (default 75 seconds). For longer generations, update all three together using the Python client and relay configuration. Local models may need more time for an initial model load.

Errors travel through the relay as safe categories: authentication, rate_limit, http_error, timeout, connection, invalid_input, invalid_response, no_text, or web_search. Provider bodies, keys and URLs are excluded from error messages. The adapters do not retry generation requests automatically, because a failed or timed-out call might already have generated billable output.

These adapters produce non-streaming text and optionally use a configured search service. They do not invoke shell commands or implement provider-specific agent workflows. Use a custom handler or the existing local A2A bridge for those workflows. --provider and --local-a2a-url are mutually exclusive.

Use from Python

import asyncio
import os
import httpx
from network_a2a.adapters import create_adapter, load_config
from network_a2a.client import AgentClient

async def main():
    config = load_config("ollama", model="llama3.2")
    async with httpx.AsyncClient() as http:
        adapter = create_adapter(config, http)
        agent = AgentClient("wss://agents.example.com/connect", os.environ["A2A_TOKEN"], adapter)
        await agent.run()

asyncio.run(main())

Add a provider by implementing HTTPAdapter.generate(messages, instructions=None) and registering a ProviderSpec in network_a2a/adapters/__init__.py. The base adapter handles input validation, concurrency, timeouts, bounded HTTP responses, and result formatting.

Connect agents across laptops, desktops, and other devices

For the desktop invitation workflow, see Invite another device. This guide is for running a separate relay or command-line agents.

  • Install
  • Create identities
  • Run on a LAN
  • Deploy with TLS
  • Connect agents
  • Reliability and capacity

This relay accepts many simultaneous device connections. Each device opens an outbound WebSocket to one reachable server. Devices can be on different networks behind NAT; only the relay needs to accept inbound traffic. Multiple agents on one device work too: give each agent a separate identity and process.

network_a2a/ provides a custom authenticated transport that can forward JSON-RPC payloads to an existing local A2A server. The relay itself is not a standard A2A endpoint and does not advertise an Agent Card. Use its device client to reach local A2A servers. Standard A2A discovery and streaming are not implemented by this relay.

1. Install on the relay and every device

Use Python 3.13 or newer. From this repository directory on Windows:

python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-network.txt

On Linux/macOS, use .venv/bin/python in place of .venv\Scripts\python. Devices need Python and this repository, or a custom client implementing the WebSocket frames documented below.

2. Create identities on the relay

.venv\Scripts\python -m network_a2a.provision laptop_alice laptop_bob desktop_charlie

This creates credentials.json with three independent random tokens. The file is excluded from Git. Keep the full file only on the relay. Privately provide each device its own token. Add further agents with unique tokens of at least 32 characters. The file has this structure (placeholders are not usable tokens):

{
  "laptop_alice": {"token": "ALICE_PRIVATE_TOKEN", "group": "team"},
  "laptop_bob": {"token": "BOB_PRIVATE_TOKEN", "group": "team"},
  "desktop_charlie": {"token": "CHARLIE_PRIVATE_TOKEN", "group": "team"}
}

Agents can see and invoke only identities with the same group. Possession of a token authorizes that identity; the headless relay has no separate login or invite UI. Group members can invoke each other's agents, so connect only handlers you intend to share. Local credentials/accounts remain on their own device. Rotate or revoke tokens by updating the file and restarting the relay; restart disconnects all devices. Protect the file with OS permissions and never put tokens in URLs.

3. Run locally or on a trusted LAN

$env:A2A_CREDENTIALS_FILE = "$PWD\credentials.json"
.venv\Scripts\python -m uvicorn network_a2a.server:app_from_env --factory --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 8454144 --ws-ping-interval 20 --ws-ping-timeout 20

For local testing, clients use ws://127.0.0.1:8000/connect. For a trusted LAN, use the relay machine's LAN IP, allow inbound TCP 8000 in its firewall, and add --allow-insecure to the client command. Plaintext LAN mode exposes traffic and tokens to the network; use the TLS deployment below for internet connections.

4. Deploy for internet access

Use an always-on VPS or other public server with Docker and Compose. Copy the repository and private credentials.json there. Point a DNS name such as agents.example.com at the server's public IP. Allow inbound TCP ports 80 and 443 through the server firewall and hosting provider firewall. Ensure outbound HTTPS works for certificate issuance. Do not publish port 8000 separately.

On that server (Linux shell):

export A2A_DOMAIN=agents.example.com
docker compose -f compose.network.yml up -d --build
docker compose -f compose.network.yml logs --tail=100

Caddy terminates TLS and forwards WebSocket traffic to the relay. Once DNS and certificate issuance succeed, devices use wss://agents.example.com/connect. The public health endpoint is https://agents.example.com/health. For image and PDF attachments, use the current relay code and the WebSocket size limit above. A separate reverse proxy must also accept request bodies of at least 8 MiB. Older relays have a 256 KiB limit and accept only text in shared chats.

Use the native desktop app's Join workspace dialog to connect to this relay with wss://agents.example.com/connect and your device token. The public server is API-only; it does not serve a browser dashboard. See the desktop guide.

A home-hosted relay needs router forwarding and a reachable public IP; carrier NAT may prevent that. A VPS avoids that dependency. Device networks must permit outbound TLS/WebSocket connections to port 443. No implementation can guarantee connectivity through a network that blocks that traffic.

5. Connect agents on different devices

On Bob's laptop, set Bob's token and run a persistent echo agent:

$env:A2A_TOKEN = 'paste-bobs-private-token'
.venv\Scripts\python -m network_a2a --server wss://agents.example.com/connect

On Charlie's desktop, run the same command with Charlie's token. On Alice's laptop, send a request to either identity using Alice's token:

$env:A2A_TOKEN = 'paste-alices-private-token'
.venv\Scripts\python -m network_a2a --server wss://agents.example.com/connect --to laptop_bob --payload '{"text":"Hello Bob"}'
.venv\Scripts\python -m network_a2a --server wss://agents.example.com/connect --to desktop_charlie --payload '{"text":"Hello Charlie"}'

The token determines the device identity. Do not start two connections using the same identity: the relay rejects duplicates. Stop a persistent process before using its token for a separate CLI connection. HTTP requests below can reuse a connected identity's token without opening another WebSocket.

To run an AI model instead of the echo handler, use --provider and --model. See provider adapters for Ollama, Bionic GPT, cloud APIs, and compatible local model servers.

Attach an existing local A2A agent

Start your existing local agent on Bob's machine, then run:

.venv\Scripts\python -m network_a2a --server wss://agents.example.com/connect --local-a2a-url http://127.0.0.1:9999/

The client forwards incoming JSON bodies to this fixed local HTTP endpoint and returns its JSON response. Send the JSON-RPC request appropriate to your agent's A2A version; the relay preserves the inner JSON-RPC request and response IDs. Set A2A_LOCAL_TOKEN if that endpoint needs Bearer authentication. The client does not forward relay tokens or give peers the ability to select local URLs. Use synchronous JSON responses; SSE and streaming are not supported here.

Integrate a custom agent in Python

import asyncio
import os
from network_a2a.client import AgentClient

async def respond(payload, sender):
    # Call your local model/agent here. Keep blocking work off the event loop.
    return {"text": f"Received from {sender}: {payload}"}

async def main():
    agent = AgentClient("wss://agents.example.com/connect", os.environ["A2A_TOKEN"], respond)
    runner = asyncio.create_task(agent.run())
    try:
        await agent.ready.wait()
        print(await agent.request("laptop_bob", {"text": "Collaborate on this task"}))
        await runner
    finally:
        runner.cancel()
        await asyncio.gather(runner, return_exceptions=True)

asyncio.run(main())

Discover and invoke over HTTPS

$headers = @{ Authorization = "Bearer $env:A2A_TOKEN" }
Invoke-RestMethod https://agents.example.com/agents -Headers $headers
Invoke-RestMethod https://agents.example.com/agents/laptop_bob/invoke -Method Post -Headers $headers -ContentType application/json -Body '{"text":"Hello via HTTPS"}'

Reliability and capacity

The client uses heartbeat pings and automatic reconnect with backoff for network failures. Unauthorized or duplicate identities stop instead of retrying forever. Requests to offline agents fail immediately. A disconnected or timed-out request is not replayed: its work may already have executed. Applications should provide idempotency keys before retrying operations with side effects.

This implementation keeps connections and in-flight requests in memory. Run one worker and one relay replica. There is no two-device limit; practical capacity depends on server resources. Defaults: 256 pending requests globally, 32 concurrent requests per connection, 8 MiB + 64 KiB frames/bodies, and a 60-second relay response timeout. Each sender has a burst of 30 and refill of 5 requests per second. Set A2A_MAX_PENDING or A2A_REQUEST_TIMEOUT (1..300 seconds) on the relay as needed. Increase client and local HTTP timeouts in code for longer work. There is no durable offline queue, persistent task store, or multi-replica routing. Use an external broker and shared storage before horizontally scaling.

Transport is encrypted from device to relay with WSS; the relay can read routed payloads. There is no end-to-end encryption between agents.

Verify

Connection Server

This development server routes client-to-client messages and can invoke relay agents. It is not needed to launch the desktop app.

Start and check the server

python -m uvicorn src.server.app:app --host localhost --port 8000

Open http://localhost:8000/health. The response is {"status":"healthy"} and does not depend on an agent being reachable.

Try messaging

Keep the server running. In a second terminal, start the receiver:

python scripts/demo_client.py client-B client-A "Hi from B"

Its initial send reports CLIENT_NOT_FOUND until client-A connects. Leave it running. In a third terminal, start the sender:

python scripts/demo_client.py client-A client-B "Hello Client B"

The receiver prints [client-B] <- client-A: Hello Client B. Successful client-to-client sends have no acknowledgement; check the receiver for delivery. Stop each process with Ctrl+C. For another server address, pass --host and --port to the demo client.

Message format

Clients connect to /ws/{client_id} and send camelCase JSON envelopes:

{
  "messageId": "msg-123",
  "type": "message",
  "source": {"id": "client-A", "type": "client"},
  "destination": {"id": "client-B", "type": "client"},
  "sessionId": "session-001",
  "timestamp": "2026-10-02T10:00:00Z",
  "payload": {"text": "Hello"}
}

The server rewrites source to the sending connection's identity. destination.type is client for socket delivery or agent for gateway invocation. Agent replies return to the requesting client with the same messageId. Client identities are self-declared and unauthenticated.

Failures return an error frame to the sender:

{
  "type": "error",
  "messageId": "msg-123",
  "code": "CLIENT_NOT_FOUND",
  "message": "Destination client 'ghost' is not connected."
}

Code

Meaning

INVALID_MESSAGE

Invalid JSON, envelope, or agent ID

CLIENT_NOT_FOUND

Destination client is not connected

AGENT_NOT_FOUND

No usable agent relay is configured

AGENT_UNAVAILABLE

Relay unreachable, or agent unknown or outside the caller's group

TIMEOUT

Gateway request timed out

A2A_ERROR

Relay rejected credentials or returned an unreadable response

INTERNAL_ERROR

Unexpected server failure; details stay in server logs

Unparseable frames may have a null messageId. Malformed messages do not close the connection, and stack traces are not sent to clients.

Current limits

  • The Connection Server has no client authentication, session management, persistent registry, or client delivery receipts. Its synchronous agent calls return correlated replies; asynchronous agent push is not implemented.
  • The relay uses a custom transport, without standard A2A discovery or streaming. It can bridge synchronous JSON requests to an existing local A2A HTTP endpoint.
  • Run the relay with one worker and one replica. Connections and in-flight requests are in memory, with no durable offline queue or automatic replay. Desktop workspaces separately persist their history and membership.
  • Shared workspaces need their host online for new requests and synchronization. WSS encrypts device-to-relay traffic; the relay can read routed payloads.
  • Local model fit estimates and automatic delegation depend on device resources, model metadata, and model behavior. They do not guarantee model capabilities.
